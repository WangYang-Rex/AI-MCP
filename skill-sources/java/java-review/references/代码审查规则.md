对当前变更的代码进行代码开发规范审查。

## 审查范围

### 审查边界：只审查本次变更引入的问题

**核心原则：不审查存量代码，只审查本次变更引入的新代码或修改代码。**

如果用户指定了文件路径，则审查指定文件：$ARGUMENTS

如果未指定文件，则合并以下两条命令的输出，获取所有变更文件（已暂存 + 未暂存 + 新增未追踪）进行审查：

1. `git diff origin/release --name-only` — 相对正式 `release` 分支的已追踪文件变更（已暂存 + 未暂存）
2. `git ls-files --others --exclude-standard` — 新增但尚未 `git add` 的文件（untracked）

如果 `origin/release` 分支不存在，依次回退为：`git diff origin/main --name-only` → `git diff HEAD~1 --name-only`（仅最近一次提交）。如果均不可用（如非 git 仓库），则提示用户手动指定需要审查的文件。

合并后去重，并**过滤出需要审查的文件类型**：仅保留 `.java` 和 MyBatis XML 文件，跳过 `.md`、`.properties`、`.json`、图片等非代码文件。

**如果过滤后没有任何需要审查的文件**（即本次变更不涉及 `.java` 或 MyBatis XML），则直接输出"本次变更不涉及 Java 代码或 MyBatis XML，无需代码审查，并生成一份无问题的审查报告。

### 分类标准

- 规则条目中标注为 **【必须遵守】** 的：违反标记为 **"MUST FIX"**
- 规则条目中标注为 **【建议遵守】** 的：违反标记为 **"SUGGEST"**
- **编码风格规范**（注释、注解、方法结构、换行）中的规则违反，除明确标注为必须遵守的条目外，默认标记为 **"SUGGEST"**

### 审查维度

## 1. 异常处理规范

- 参数校验失败抛 `ParameterException`（中文错误信息），如：`throw new ParameterException("配置名称不能为空")`
- Controller 层方法声明 `throws ParameterException`，由全局处理器捕获
- 空集合等非异常场景使用提前 return
- **禁止吞异常**：catch 中必须记录 `log.error`
- **异常日志必须包含堆栈信息**：异常对象 `e` 作为 `log.error` 的最后一个参数传入
- **异常日志必须包含业务上下文**：如 `corpId`、`orderCode` 等关键字段

## 2. 日志规范

- 推荐使用 `@Slf4j` 注解（Lombok），缺少 `@Slf4j` 审查按 SUGGEST；不建议手动创建 Logger
- 日志信息使用**中文**描述
- 格式：`类名.方法名 + 描述 + 关键参数`，如：`log.info("XxxService.method 开始处理 corpId={}", corpId)`
- 使用 `{}` 占位符，不用字符串拼接
- 错误日志把异常对象作为最后一个参数传入 `log.error`
- 复杂对象用 `JSONObject.toJSONString()` 序列化后打印


## 3. Import 组织顺序

按以下顺序组织，各组之间空一行：`com.alibaba.*` → `com.raycloud.*` → `lombok.*` → `org.apache.*` → `org.springframework.*` → `javax.*` → `java.*`

- `static import` 置于对应包组的非 static import 之后、下一组之前，与其所属包同组排列


## 4. 性能规范

- **禁止 N+1 查询**：循环内不得重复调用 DAO、Dubbo、HTTP 等远程或数据库查询；必须改为批量查询后在内存中按 key 映射处理
- **禁止循环内重复构造高成本对象**：如正则、日期格式化器、大对象 JSON 序列化等，能提前构造或复用的必须提前处理
- **批量数据处理必须控制规模**：批量查询、批量写入、导出等场景必须分页、分批或设置合理上限，避免一次性加载过多数据导致内存或数据库压力
- **数据库查询必须避免全表扫描**：查询条件应命中索引；新增复杂查询时需关注 SQL 条件、排序字段、分页方式是否会导致慢查询
- **日志输出必须控制成本**：禁止在高频循环或大批量数据处理中打印大量日志；复杂对象序列化日志需确认必要性并控制数据量
- **远程调用必须避免串行放大**：多条数据需要远程补充信息时，优先使用批量接口；无批量接口时需评估调用次数和失败影响

## 5. 代码开发规范

### 【必须遵守】

1. **单一职责原则**：每个类和方法只处理一个逻辑
2. **方法长度**：不超过 100 行，过长须拆分为多个小方法
3. **类长度**：不超过 800 行，超出须拆分类或引入设计模式
4. **嵌套限制**：**禁止超过三层**循环和条件嵌套，通过方法提取或提前 return 减少层级；嵌套层级按 `if` / `else if` / `for` / `while` / `do while` / `switch` / `try-catch` / lambda 块等控制结构叠加计算，例如 `if → for → if → if` 已达到 4 层，必须标记为 MUST FIX
   - `else if` / `else` 与对应的 `if` 视为同级，不额外增加层级（如 `if → else if → else` 为 1 层）
   - `try-catch` 包裹的代码块内部从 0 开始重新计算嵌套层级（`try` 本身占 1 层）
   - lambda 内部独立计算嵌套层级（lambda 自身占 1 层，内部从 0 开始）
5. **参数个数**：不超过 8 个，推荐 5 个以内；超出时封装为请求对象
6. **参数类型**：使用明确的 Java 类型，**尽量避免** `JSONObject` 或 `Map` 作为方法参数
7. **方法签名类型**：方法参数、返回值、泛型声明禁止直接使用全限定类名（如 `java.util.List<com.xxx.XxxVO>`、`com.xxx.XxxRequest`），必须通过 `import` 引入后使用简短类型名
8. **复杂逻辑设计模式**：复杂分支、复杂流程编排、多个业务类型差异化处理等场景，必须使用合适的设计模式（策略、模板方法等）拆分职责，避免大段 `if/else` 或单方法堆叠逻辑
9. **禁止魔法值**：代码中不得直接出现无语义的数字、字符串、状态码、类型码等魔法值；必须使用枚举类或常量类定义，并通过有语义的名称引用；如果系统中已经存在该魔法值的定义，必须直接引用已有定义，禁止重复新建
10. **SQL 关联查询限制**：分析变更的 `mapper.xml` 时，关联查询不允许超过 2 张表的 `join` 关联

### 【建议遵守】

1. **命名规则**：类名使用 PascalCase，避免缩写
2. **方法处理逻辑**：避免修改方法参数，优先使用返回值传递结果
3. **迭代需求**：代码要符合原有代码业务逻辑和结构，不要破坏既有逻辑
4. **单元测试**：业务逻辑类测试覆盖率 80% 以上
5. **表字段扩展**：分析 `mapper.xml` 和对应表的 PO 加新字段时，要符合当前 PO 对应表的基本含义；如果不符合，建议新建扩展表承载


## 6. 通用原则

1. **多租户**：所有数据操作必须带 `corpId` 过滤，防止数据越权
2. **事务**：方法内存在多次数据库操作，且数据库操作包含新增、删除、修改时加 `@Transactional(rollbackFor = Exception.class)`；单次写库或只读查询不强制加事务
3. **空值防御**：按 [编码风格规范-方法结构](编码风格规范-方法结构.md) §四 执行
4. **序列化**：跨 Dubbo 传输的对象必须实现 `Serializable`，建议定义 `serialVersionUID`（缺少 `serialVersionUID` 审查按 SUGGEST）
5. **JSON 工具**：优先使用 `FastJSON`（`JSONObject.toJSONString()`、`JSONObject.parseObject()`）
6. **Bean 拷贝**：使用 `BeanCopyUtil`（项目内工具类）
7. **集合工具**：优先使用 Apache Commons Collections（`CollectionUtils`、`MapUtils`）
8. **字符串工具**：使用 `org.apache.commons.lang.StringUtils` 或 `org.apache.commons.lang3.StringUtils`
9. **响应包装**：Controller 返回值统一用 `Response.success(data)` 包装
10. **组件字段解析**：涉及解析、加载组件字段时，必须使用组件仓库公共解析类加载组件仓库，如 `ComponentRepositoryAssembler.buildComponentOperatorRepository` 或 `ComponentOperatorFactory.getInstance`，禁止直接使用 `JSONObject` 解析组件字段


## 输出格式

详细问题列表中的每一条问题项都必须填写 `修改建议`，且建议必须具体、可执行，说明应如何改代码或调整实现；禁止填写 `-`、`无`、`建议优化`、`按规范修改` 等空泛内容。

报告内容格式如下：

```
# 代码审查报告

**项目路径**：{项目路径}
**审查时间**：{yyyy-MM-dd HH:mm:ss}
**审查分支**：{当前分支名}

## 审查摘要

- 审查文件数：X
- MUST FIX：X 项
- SUGGEST：X 项

## 详细问题列表

### MUST FIX

| # | 文件 | 行号 | 规则 | 问题描述 | 修改建议 |
|---|------|------|------|---------|---------|
| 1 | `文件路径` | L100-L200 | 方法长度 | 方法 xxx 超过 100 行（实际 150 行） | 拆分为 validateXxx、buildXxx、saveXxx |

### SUGGEST

| # | 文件 | 行号 | 规则 | 问题描述 | 修改建议 |
|---|------|------|------|---------|---------|
| 1 | `文件路径` | L50 | 方法处理逻辑 | 方法 enrichOrder 直接修改入参 | 使用 BeanCopyUtil 拷贝后修改并返回 |

## 无问题文件

- `文件路径1` ✅
- `文件路径2` ✅
```

如果所有文件均无问题，报告内容为："所有变更文件均符合代码开发规范，无需修改。"
