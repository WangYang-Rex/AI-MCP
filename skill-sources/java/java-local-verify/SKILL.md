# Java 本地验证

验证当前 Java 改动是否达到用户需要的可信程度。优先使用项目已有的 Maven Wrapper、构建说明、CI 配置和测试方式；不要把某个项目示例中的分支名、profile、模块名或版本号套用到其他项目。

## 安全边界

- 先做只读检查。保留用户的未提交改动；未经请求，不切换分支、不拉取代码、不清理工作区、不改 POM、不提交。
- 只使用明确的本地或测试配置。若启动可能连接生产环境、修改共享数据或需要未知密钥，停在启动前并说明需要用户确认的配置。
- 不为通过验证而跳过、删除或弱化失败的测试。
- 构建生成的 `target/` 等正常产物可以保留；如果产生意外文件，在结果中列出。

## 工作流

### 1. 确定验证对象

定位所有相关 Git 仓库和 Maven 根目录，读取适用的 `AGENTS.md`、项目构建说明、根 `pom.xml`、`.mvn/` 与 CI 配置。检查：

- 当前分支、工作区状态、基准分支或提交；
- 实际 diff、受影响模块以及调用它们的下游模块；
- parent、BOM、内部 API/SDK 的坐标和版本是否匹配；
- 项目要求的 JDK、Maven、profile 与本地仓库设置。

如果待验证分支与基准指向同一提交且没有工作区 diff，将本次定义为“基线验证”，不可声称验证了需求改动。

### 2. 选择最小可信命令

优先执行 `./mvnw`，没有 Wrapper 时才使用环境中的 `mvn`。从项目配置中确定参数，不默认添加 `-P local`、`-o` 或 `-DskipTests`。

多仓库或内部依赖场景：先构建发生改动且下游需要的上游模块，再构建下游。常见形态是：

```bash
./mvnw -pl <上游模块> -am install
./mvnw -pl <下游模块> -am test
```

仅当依赖已经完整缓存在本地时使用离线模式。仓库访问失败时，区分“代码失败”和“环境/依赖获取失败”，不要用离线编译结果掩盖未执行的验证。

### 3. 逐级验证

根据改动和项目能力尽量推进以下层级；较高层级不能反向证明未执行的层级：

1. **改动确认**：每个待验证改动都出现在 diff 中，范围与用户描述一致。
2. **编译验证**：编译受影响模块及必要的依赖模块。使用 `-DskipTests` 的结果只能记为“编译通过”。
3. **测试验证**：运行受影响模块的单元测试；项目有标准 `verify` 阶段时继续运行集成测试和质量插件。记录测试数量、跳过数量与失败原因。
4. **启动验证**：对可安全本地启动的服务使用项目规定的本地/测试配置，等待明确的健康信号，并检查启动日志。启动后停止由本次验证创建的进程。
5. **功能验证**：只验证与改动有关且有明确契约的接口或业务路径，包括正常输入、关键边界和必要的数据副作用。优先复用项目现有集成测试、HTTP 样例或 API 文档，不猜测接口、凭据和期望结果。

若完整多模块构建代价过高，先验证受影响模块及其直接下游，再说明尚未覆盖的全量范围。失败后先定位首个有因果意义的错误；修复代码不属于本技能，除非用户另行请求。

### 4. 给出可审计结论

最终结果至少包含：

- 验证对象：仓库、分支/提交、diff 范围与受影响模块；
- 环境：JDK、Maven、profile，以及多仓库依赖版本；
- 实际执行的命令及每条命令的结果；
- 分级状态：改动确认、编译、测试、启动、功能分别标为通过、失败或未执行；
- 最高可信结论与剩余风险。

结论使用精确措辞：

- 只有编译成功：**编译通过，功能未验证**；
- 测试成功但未启动：**自动化测试通过，运行时未验证**；
- 服务成功启动：**启动通过，业务功能未验证**；
- 相关接口及副作用符合契约：**本次改动的目标功能已验证**；
- 没有独立改动：**仅完成基线验证**。

不要用“验证完成”概括存在未执行层级的结果。
