### 业务部门的构成与运转

正式分享之前，咱们先分析一下业务部门的构成和运转
业务部门一般有
售前：电销/直销/渠道
售后：客成/客服/实施
产研：产品/技术
…
业务部门的产品一般为  软件产品
大家日常的工作都是围绕软件产品研发、迭代与运营，售卖 实施与交付

### 现状与困境

不知道其他部门怎么样，我们部门呢，产品经理是非常受欢迎的

销售这边有几十万的大客户的业务流程需要一起跟进出方案 
实施这边客户又提出了新的诉求 功能不能完全满足，闹着退款 
技术这边也想找产品确认某个复杂需求的细节

产品同学呢也很苦恼，每天各种对接，参加客户会议，经常没时间好好出需求，紧急工单经常堆积
这些呢大概是业务部门的运转现状，一切呢平稳有序

直到今年初，来了一些新人，特别是产品经理换了新人
- 一边需要深入理解产品功能逻辑
- 一边对接售前售后，参加客户会议，对接用户需求，出KA用户解决方案
- 1个产品要对接17个技术
- 工单堆积，PRD产出较少，高危客户剧增
由于对于软件产品不够熟悉，整个部门的运转开始出现问题

以上是大概的背景

## OpenClaw 简介

### 核心组件

| 组件 | 职责 |
|------|------|
| **Gateway** | 网关，常驻守护进程，WebSocket 服务，所有通信的中枢 |
| **Agent Runtime** | Agent运行时 内置 Agent 循环：Prompt 组装 → LLM 调用 → 工具执行 → 结果回传 |
| **Channels** | 频道，可以链接各种IM工具：WhatsApp/Telegram/Slack/Discord/Signal/钉钉/飞书/WebChat 等 | Openclaw是最早打通各大平台通信问题的产品
| **Sessions** | 会话管理 |
| **Tools** | 内置工具（exec/read/write/browser 等）+ 插件工具 |
| **Skills** | 内置技能+自己安装的技能 |
| **Cron** | 定时任务调度（提醒、定期巡检、Dreaming 等） |
| **Memory** | 记忆系统，跨会话持久化 |

三层记忆体系
1. MEMORY.md — 长期记忆（精华层）
2. memory/YYYY-MM-DD.md — 日记忆（工作层）
3. DREAMS.md — 梦境日记（巩固层）
4. knowledge/ — Obsidian 知识库（共享层）

### 多 Agent 能力

OpenClaw 支持配置多个 Agent
比如产品Agent 小策 
技术Agent 小工
每个 Agent 有独立的：
- **Workspace**（工作目录 + 引导文件）
- **Session 存储**
- **Memory 索引**
- **Skills 配置**

可以互相协作调度处理复杂问题

## 痛点

- 以前 新人要花很长时间熟悉产品，难以精通，产品培训难，现在 借助产品Agent可以快速上手 熟悉产品
- 以前 客户业务场景复杂，花大量时间研究用户场景，出对接方案 现在 可以让产品Agent分析客户场景，产出方案初稿
- 客户给了个word文档，说能不能实现，头都大了 现在 可以让产品Agent分析，技术Agent分析，给出可落地的可行性方案
- 产品忙于各种对接，焦头烂额，没时间出需求 现在 产品可以有更多的时间研究业务，打磨产品
- 以前 技术疲于应付大量线上问题（功能使用问题/功能不满足，需要找产品出需求/Bug），没时间做需求。现在 线上问题先由产品和技术助理初筛拦截，技术同学得以专注于核心需求迭代与解决真实Bug，大幅提高交付效率。
